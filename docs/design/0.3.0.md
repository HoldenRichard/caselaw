# caselaw 0.3.0: the design

Agreed with Holden on 2026-10-30 in five rounds of questions. The research it draws on is the semester study of his agent-built development (the defect ledger cited here as DEF-NNN) and the literature read for it. This file is the plan of record for 0.3.0; changes to it are proposed and ratified like anything else here.

## Context

**caselaw today:**
- Public on GitHub (HoldenRichard/caselaw); npm has 0.1.0. Locally it's v0.2.0, 35 commits, with 577 running tests.
- Its doctrine is "it ships zero rules". It works through an interview, an authority split, a close-out and a rule ladder (memory, then checklist, then gate). Gates are born as warnings and earn `block`. It also has an audit and a review prompt.

**The goal:** a generalized update that draws on the whole study and on the literature read for it. It should make every project's harness adaptive and optimized to its owner, with the agent doing most of the work. The hackathon's custom harness comes later and isn't scheduled.

**Already done (10-30):** DEF-748 (the false "shipped to the App Store" line) is fixed locally in caselaw@a8d4e01. It isn't pushed yet, so the public README still has the false line.

## Decisions (grilled with Holden, 10-30)

### Layers

1. **Defaults:** active at install. A rule qualifies only if it recurred in two or more of Holden's projects and is principle-level. There's no fixed cap; the optimizer keeps the set trimmed. A default enters at the memory rung, with the study's incidents as precedent. Its first local catch adds the project's own Origin. If it catches nothing in 60 days with commits, it's proposed for demotion (the window is configurable).

   | # | Default | Absorbs |
   |---|---|---|
   | D1 | Claims are re-derived, not carried, both premises received and claims sent out | the trace-the-premise candidate |
   | D2 | A check counts once it has been seen to fail; report the verdict, not "completed" | |
   | D3 | A check states what it did not cover | |
   | D4 | One writer per working tree; stage explicit paths | the one-writer-per-repo candidate |
   | D5 | Outward-facing, irreversible or spending actions wait for the human; words sent in the human's voice are the human's | |
   | D6 | A dependent step never runs after the step before it failed | |

2. **Environment triggers:** detection or an interview answer proposes rules, with the triggering fact shown.

   | Trigger | Proposes |
   |---|---|
   | T1: an outside gatekeeper | the declarations register, retain-generation-records, the outward-facing tier |
   | T2: public claims | declarations register entries, each with a re-derive command |
   | T3: several agent tools or parallel sessions | D4 climbs to a pre-commit writer guard |
   | T4: paid or metered APIs | a spend protocol |
   | T5: dated records | times come from the clock |
   | T6: secrets | the secrets rule |
   | T7: several config identities | config-identity-gate |

   The default is propose-and-ratify. `answers.json` holds one global switch with per-trigger overrides.

3. **Failure-born rules:** propose at a catch, then the human ratifies, as now. C1 applies: a rule counts once it has caught the failure it came from.

4. **The optimizer** handles compaction and trimming together.
   - **Actions:**
     - mechanize: memory becomes a gate, the main compaction;
     - merge overlapping rules, keeping every Origin;
     - demote or retire to the candidates or an archive, never deleting;
     - archive precedent, so a loaded rule is just its statement and trigger;
     - drop stale references.
   - **Signals:**
     - the governance text loaded at session start exceeds a budget (the default set from the field test);
     - five rules ratified since the last pass;
     - the monthly audit;
     - agent trouble: three catches of an active rule's class, or frequent context compactions where the tool exposes them.
   - **Safeguards:**
     - everything is proposed and ratified;
     - merges are lossless and re-derived, never paraphrased (DEF-225);
     - `doctor` re-checks loading and injection afterwards (P6).

5. **Self-update:** the agent may propose changes to every part of the harness: the defaults, triggers, optimizer settings, interview and docs. Each change cites local evidence and is itself a rule with an Origin.
   - **Auto bounds:** when a mechanism is set to auto, strengthening changes and parameter tuning apply within bounds (at most ±25% and once a week per mechanism). Everything else is proposed.
   - **C1 for the harness:** every change names the signal it should improve. The audit checks it after its window, and the agent proposes reverting changes that didn't help.

6. **The constitution:** always needs the human, under any setting.
   1. Any change that weakens enforcement or widens the agent's authority.
   2. The append-only evidence trail.
   3. Reversibility: archive, never delete.
   4. D5 actions never become automatic.
   5. The constitution itself.

7. **The personal layer:** stored locally in the home folder, with no telemetry; sharing is a manual export. A rule that has caught failures in two or more of the owner's repos is proposed as a personal default for new installs.

### Onboarding (about three minutes, five screens)

The agent path: the agent runs `init` in draft mode and pre-fills every answer it can, each with its evidence. The human confirms the five screens in chat or in the terminal. The CLI interview stays for people without an agent. Every screen accepts "I don't know", written down as a visible gap.

1. **Autonomy preset:** Ask me first (preselected), Tune itself, or Custom. One line says the constitution always applies.
2. **What the agent can't do or observe:** physical, chosen or untested.
3. **Outside authority and public claims:** pre-filled from detection; the human confirms.
4. **Defaults:** D1–D6 plus any personal defaults, each with where it caught failures. Accept all, or pick.
5. **Proposed triggers:** accept all, or pick.

### Also in 0.3.0

- **Review roles:** refuter, verifier and judge prompts, each for a different model where possible. Reviewers get the diff and the claim, never the builder's reasoning, and return an explicit pass or fail.
- **Doctrine docs:** C1, the reach scale (a "local patch" rung goes below memory), what the study did not establish (no velocity or reliability claims), the day-one answer, and related work, with each source cited only for what it supports (DEF-738).
- **README:** "ships few rules, and earns the rest". A claims test covers every number and status statement.

## Verification

- `npm test` and `npm run typecheck` pass. Every new check, gate kind, trigger and optimizer action has a positive control: a known-bad input that must fail.
- Constitution tests: an auto-mode agent change that weakens enforcement must be refused and turned into a proposal.
- The claims test covers the README and methodology. `doctor` and `init --dry-run` run on the fixtures, with golden renders for each adapter.
- A field-test scoring table for every repo. DEF-274 closes at the agreed bar.
- `doctor` confirms after every optimizer pass that every rule still loads and is injected.
