The defect: on ntfy, homebridge and pyvisa the generated docs scored 1/5 for specificity and
"would not merge" (2026-09-06). The bar for closing it, set before this run: at least 4/5 and
"would merge" on two of the three.

## Method

Fresh shallow clones (ntfy 08566a0, homebridge edf5493, pyvisa a5b56ab). The agent (Claude Code,
Opus 5.5) ran `caselaw init --draft` on each, read the repository's README, contributing guide, CI
and release workflows, filled every answer with file-and-line evidence, and ran
`init --from-draft --yes --force`. No human reviewed these answers: `--yes` stood in for the
confirmation, so the provenance rows that say "in chat (--yes)" are not true of this run.
`--force` overrode the refusal to write into a docs/ that TypeDoc (homebridge) and MkDocs (ntfy)
own. Scoring was done by a separate agent (Claude Sonnet) that saw only the repositories, the
generated docs and the rubric, not the drafting agent's reasoning.

## What held it down, and what follows

1. **Releases are triggered by a push.** Pushing any tag publishes pyvisa to PyPI
   (`release.yml`, `tags: "*"`); a `beta-*` or `alpha-*` branch publishes homebridge to npm, and
   homebridge's own CLAUDE.md tells agents to create those branches; a `v*.*.*` tag releases ntfy.
   "Release console: chosen" hid all three. Detect publish steps and their triggers from CI, and
   state what a push publishes (D5: outward-facing actions wait for the human).
2. **Detected commands were generic, not the project's gates.** ntfy's `go test ./...` fails on a
   fresh checkout (embedded `site`/`docs` must be built first; `make docs web` then `make check`);
   pyvisa's CI runs `ruff format --check`, `ruff check pyvisa`, `mypy pyvisa`. Prefer the commands
   CI and the Makefile run, and let a draft correct the detected ones with evidence.
3. **Declarations registers were empty forms.** Nothing collected the claims themselves. The draft
   should carry them, each with evidence; a surface with no recorded claim should not render as a
   row of holes.
4. **docs/ is often someone else's.** On two of three repositories a documentation generator owns
   it. A configurable doctrine directory is needed before a stranger's repository can take this.
5. **The close-out and pointer were boilerplate**, identical across the three. They should carry
   the project's real gates and its human proof.
6. **The drafting agent made three unsupported claims** ("the hosted ntfy.sh is not for testing";
   the Connectivity Standards Alliance as an authority over homebridge, which says it is
   unaffiliated; "hardware" for homebridge's core, which talks to controllers, not devices). The
   validator checks that evidence exists, not that it supports the claim, and `--yes` skipped the
   human who would have caught them. The confirmation step should show the cited lines themselves.
   Detection also over-read HAP and Matter libraries as hardware; they mean pairing with a
   controller, which deserves its own option.
7. **An untested boundary rendered "not recorded" as its reason**, because no question collects
   one. The draft should carry a reason per untested boundary.

triggers, the iOS-delivery caveat). What remains:

1. **Publishing ignored job conditions.** pyvisa's workflow starts by hand, on a schedule or on any
   tag, but its publish job runs only on a push (`if: github.event_name == 'push'`), and the
   GitHub release job needs it. Listing every trigger was a factual error in the safety-critical
   section. Read job `if:` and `needs:`.
2. **Destinations were vague.** "A git push made by CI" did not name the repository it pushes to;
   "the Makefile's release target" did not say what it releases (Docker Hub, GoReleaser packages).
3. **Gates without their conditions.** ntfy's CI tests run against a Postgres service and S3

4. **Existing agent instructions were not read.** homebridge's own CLAUDE.md tells agents to target

6. **Detected commands were duplicated** under the agent's own answer, tagged "unverified".
7. **Drafting errors, again:** "the Keysight suite runs only on the buildbot" (it has a local
   loopback mode), and ntfy's "chosen" bans cited lines that do not support them. The tool cannot

Drafting errors (the agent's draft, not caselaw's output):

1. pyvisa: the untested boundary was drafted as "run the full test suite". The reason given was right
   (the Keysight-assisted tests need Keysight's software), but CI runs pytest on 15 combinations on

   that subset.
2. pyvisa: "Tested with Python 3.10+" was marked checked against `pyproject.toml` and the CI matrix,
   but `azure-pipelines.yml:27` builds its Keysight environment with `python=3.9`. caselaw does not read
   Azure Pipelines, and the draft did not look.

caselaw's output, fixable, taken next:

1. ntfy: "in its order" across `build.yaml`'s two parallel jobs, and the gate list drops
   `make build-deps-ubuntu`, which both workflows run first, so the list does not run on a clean
   machine. Gates belong to their job, and the setup CI runs first is a prerequisite to name.
2. homebridge: the close-out's Published? item pastes the full 600-character job condition. The
   authority split is the place for it in full; the checklist should point there.
3. homebridge: "the package registry's policies" never says npm.
4. homebridge: `release.yml:130-143` announces every publish to Discord through a webhook; that is a
   publish, and it is not listed.
5. pyvisa: Read the Docs builds from `.readthedocs.yaml` and is not listed as a publisher; Azure
   Pipelines is a second CI that caselaw does not read and does not say it did not read.
6. A draft that marks "the full test suite" untested while CI runs the test runner on every change
   should be questioned at review, not accepted silently (the source of drafting error 1).

Omissions the scorer named that stay as they are for now: ntfy's prerequisites beyond CI's own setup
